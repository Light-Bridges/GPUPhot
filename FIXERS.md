# GPUPhot Fixers and Potential Improvements

**Version:** 1.1
**Date:** 2024-08-02

This document tracks identified issues, inconsistencies, and potential areas for improvement within the `GPUPhot` codebase.

## 1. Parameter Inconsistencies

**File:** `callgraph/PARAMETER_CONSISTENCY.md`

### Issue
There are discrepancies between the default values of processing parameters defined in `DefaultConfig.DEFAULT_PROCESSING_PARAMS` and the default values in the signatures of the functions that consume them.

-   **`border`**: Config default is `20`, but `calibrate_image` function default is `10`.
-   **`color_range`**: Config default is `0.6`, but `get_zeropoint` function default is `0.3`.
-   **`tile_section_psf`**: Config default is `3000`, but `calibrate_image` function default is `2500`.

### Impact
This can lead to inconsistent behavior if low-level functions are called directly, as they will use different defaults than the main processing pipeline.

### Recommendation
Unify the default values. The function signatures in `photo_gpu.py` and other modules should be updated to match the values in `DEFAULT_PROCESSING_PARAMS`. This establishes a single source of truth for default behavior.

## 2. Dynamic GPU Assignment in Launcher Scripts

**Files:** `launch_gpuphot.sh`, `launch_external_worker.sh`

### Issue
Both launcher scripts contain a legacy, commented-out block that attempts to dynamically assign GPU IDs to running containers by executing a `sed` command inside them (`docker compose exec ...`). This method is fragile and not recommended for several reasons:
-   **Container Naming:** It relies on predicting the container names generated by Docker Compose (e.g., `project_service_1`), which can change based on the directory name or compose project name.
-   **State Modification:** It modifies the state of a running container (`/etc/environment`), which goes against the principle of immutable infrastructure.
-   **Race Conditions:** It's not guaranteed that the container is fully ready to accept `exec` commands immediately after `up`.

### Recommendation
The current, correct approach is to use the `deploy` key in the `docker-compose.yml` and `docker-compose.worker.yml` files to declaratively assign GPUs. The application code inside the container should then read the `NVIDIA_VISIBLE_DEVICES` environment variable, which is automatically and reliably set by the NVIDIA container runtime.

The legacy blocks in both scripts should be **removed** to avoid confusion and prevent accidental use. The documentation within the scripts has already been updated to reflect that this is a non-preferred method.

**Example of the correct approach in a Docker Compose file:**
```yaml
services:
  gpuphot_worker:
    deploy:
      replicas: 1 # This is managed by the --scale flag in the scripts
      resources:
        reservations:
          devices:
            - driver: nvidia
              count: 1
              capabilities: [gpu]
```
This configuration ensures that each instance of the `gpuphot_worker` service is allocated its own unique GPU by Docker, which is the standard and most robust practice.
